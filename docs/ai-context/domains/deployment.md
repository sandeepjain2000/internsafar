Path B does **not** mean “never touch RDS.” It means do not run the full migrate/Path C wipe path. If new columns would leave blanks that break gates, fill those values in a controlled one-time step.

## General runbook — shipping local/Vercel changes to AWS when schema changed

Local and Vercel share Supabase, so a change that "works on Vercel" has only been proven against Supabase. AWS RDS is separate and holds real accounts. Full procedure: skill `.agents/skills/ip-trace-aws-path-b-schema-gap/SKILL.md`; the newest dated plan in workspace `aws deploy/AWS-PUSH-PLAN-SCHEMA-BACKFILL-<date>.md` is the template (latest **2026-10-08**). Order:

1. **Scope** — `git diff <commit on AWS>` + untracked files (the tar is built from the working tree). List migrations (`scripts/MIGRATION_MANIFEST.txt`), `ensure*` helpers, CHECK/constraint changes, new validation rules, env var names, `package.json`/lockfile, cron.
2. **Read-only compare both DBs** — run the same read-only script on Supabase and on RDS (piped over SSH into `~/internship-portal/scripts/`, `BEGIN READ ONLY … ROLLBACK`, deleted straight after; template `aws deploy/schema-check-2026-10-08/ro-prod-safety-check.mjs`). Diff columns + PK/FK/UNIQUE/CHECK; ignore RDS `*_not_null` naming and local-only `ip_schema_flags`. Check the app DB user can do what the `ensure*` helpers do (owns tables, CREATE in `public`, REFERENCES).
3. **Per gap, one row** — what reads it · what happens if deployed without the SQL (does an `ensure*` self-create it? does a gate read the blank?) · AWS rows affected · fill needed? · fill value that keeps today's behaviour. NULL/default that already equals today's behaviour → say "no fill".
4. **Per account on AWS** — run every changed rule against real rows (names, posting fields, statuses, documents), especially non-core employers with live postings and applicants. Gate files (`auth.js`, `ipEmployerPostingGate.js`, `ipEmployerEmailVerify.js`) unchanged → login/posting unchanged. List who any new cron/email job would contact.
5. **Write the dated plan** (gaps, fills, per-account verdict, non-schema, tar contents, execution order, rollback, owner decisions) and **stop for owner approval**.
6. **Execute in this order** — re-run the read-only check (stop if different) → RDS snapshot or JSON backup → additive DDL + any fill/flag in **one transaction** via a temp runner (deleted after) → verify → remove temp files locally → `scripts/build-aws-handoff.ps1` → build-then-swap on EC2 → poll `/login` → smoke (HTTP 200s, 401 not 500, quiet error log, read-only DB re-check of the accounts named in step 4) → env/cron changes last (back up `.env`, add only). EC2 has 1.9 GB RAM and **no swap**: `next build` beside the running app can be OOM-killed (2026-10-08) — the deploy script adds a temporary 2 GB swap file for the build and removes it after. Constraint checks on RDS (PG 18) must filter `contype IN ('c','f','p','u')` because NOT NULL also appears as `contype = 'n'`.
7. **After** — update this file, `domains/database.md`, `PROJECT_INDEX.md` known-gaps row; rebuild the zip.

Old code keeps running between the SQL and the swap, so every DDL must be additive and ignorable by the old code.
